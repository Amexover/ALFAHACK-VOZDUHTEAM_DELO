# Выпуск отдела сотрудников Т1–Т4

Идентификатор: `delo-staff-2026-10-22-v1`. Миграция `20261022_01`.
Скоринг `RS-2026.10.1`, политика приёма `AP-2026.10.1`.
Контрольные суммы исходников — [RELEASE.json](../RELEASE.json).

## Чистый запуск

```sh
docker compose up -d --build
```

База PostgreSQL, API и frontend собираются из исходников; штатный запуск сам создаёт
пустую схему и демонстрационные данные. Для учёта версии схемы: `docker compose exec
api python -m alembic upgrade head`. Верификатор `verifier/demo`, андеррайтер
`underwriter/demo`; прежний `staff/demo` сохраняет права. Это демонстрационные учётные записи.

## Полная коллекция и PostgreSQL

Использовать отдельный Compose-проект, без `.env` рабочего стенда:

```sh
docker compose -p delo-staff-t4 -f docker-compose.yml -f deploy/compose.staff-check.yml up -d --build
docker compose -p delo-staff-t4 -f docker-compose.yml -f deploy/compose.staff-check.yml exec -T api python -m scripts.prepare_staff_fixture --isolated
npx newman@6.2.1 run docs/Delo.postman_collection.json --env-var baseUrl=http://127.0.0.1:8081
docker compose -p delo-staff-t4 -f docker-compose.yml -f deploy/compose.staff-check.yml exec -T api python -m scripts.check_staff_concurrency --isolated
```

Коллекция создаёт заявки и принимает решения, поэтому её прогоняют на отдельной базе.
Повторный полный прогон требует новой отдельной базы либо другого Compose-проекта.
Фикстура только добавляет специальную заявку, существующие данные не сбрасывает.
Проверка конкуренции требует PostgreSQL: два приёма, две отмены, два решения;
фиксируется один автоотказ, одна отмена и одно активное окончательное решение.

## Обновление существующего VPS

Рабочий каталог `/opt/delo`, его Compose-файлы и `.env` сохраняются. Корневой Compose
из исходников предназначен для чистого запуска и не заменяет серверную конфигурацию.
Перед переключением выполняются следующие шаги:

1. Проверить актуальный `main`, отсутствие сторонних изменений backend на сервере,
   собрать кандидата в `/opt/delo/releases/delo-staff-2026-10-22-v1/candidate`.
2. Сохранить `pg_dump -Fc`, прежний backend, серверные Compose-файлы и тег прежнего образа.
   Каталог резервной копии закрыт правами 700, dump — 600.
3. Восстановить dump в отдельную базу `delo_copy` отдельного проекта. Проверить миграцию,
   повторный запуск, откат и повторную миграцию. `scripts.check_preserved_rows` сравнивает
   SHA-256 каждой прежней строки, а не только количество строк.
4. На отдельной чистой базе пройти коллекцию и конкурентный сценарий; собрать оба образа.
5. Остановить только рабочий API, сделать финальный dump и снимок прежних строк.
   Накатить миграцию новым образом через прежний Compose. Повторить миграцию для проверки
   идемпотентности и сравнить строки до запуска нового API.
6. Обновить backend, тег API и документы. Поднять API, дождаться `/api/health`, обновить
   соединение nginx с API перезапуском frontend. Том PostgreSQL и `.env` не пересоздаются.
7. Пройти `python -m scripts.staff_live_smoke`: создаётся отдельная синтетическая компания,
   заявка проходит верификацию, андеррайтинг, решение и принятие. Повторить с `--verify`
   после перезапуска API: сохранены итог и снимки. Прежние демонстрационные заявки не правятся.

## Откат

Восстановить прежний тег API и backend из `backend-and-compose.tgz`, поднять API и
перезапустить frontend. Добавленные таблицы совместимы со старым приложением; при
откате кода их удалять не нужно. `alembic downgrade base` на рабочем сервере удалит
внутренний аудит и снимки — для обычного отката кода эта команда не используется.
Dump служит аварийной копией; восстановление поверх рабочей базы требует отдельного
решения о потере данных, добавленных после резервирования.

Состояние фактического выпуска и результаты: [TICKET_04_ACCEPTANCE.md](../docs/staff-pipeline/TICKET_04_ACCEPTANCE.md).

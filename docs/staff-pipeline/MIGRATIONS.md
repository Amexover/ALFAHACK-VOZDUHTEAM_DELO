# Миграции базы данных

Закрывает пункт, который до нас оставался открытым: изменения схемы раскатываются на уже
заполненную базу штатным инструментом, без потери данных и без пересоздания тома.

## Как это устроено

Инструмент — Alembic. Адрес базы берётся из `DATABASE_URL` приложения (`migrations/env.py`),
поэтому миграции всегда смотрят на ту же базу, с которой работает API.

Создание таблиц при старте (`Base.metadata.create_all` в `app/seed.py`) оставлено как есть:
на чистой машине проект по-прежнему поднимается одной командой и ничего не требует вручную.
Alembic отвечает за другое — за изменения схемы на базе, где данные уже есть.

Ревизия `20261022_01` только **добавляет** четыре таблицы отдела:

| Таблица | Зачем |
|---|---|
| `staff_profiles` | роль сотрудника внутри отдела и признак, применяются ли к нему правила конвейера |
| `application_pipeline` | этап, исполнитель и время этапа по заявке |
| `pipeline_events` | внутренняя история обработки |
| `score_snapshots` | снимки оценки по версиям набора правил |

Существующие таблицы не меняются вообще: ни одной новой колонки в `users`, `applications`,
`companies` или `application_events`. Роль внутри отдела лежит в отдельной таблице — так
общий перечень ролей остаётся прежним, а маскировка ФИО сотрудника под «Банк» в клиентской
истории продолжает работать.

Каждое создание в ревизии проверяется по факту наличия таблицы и индекса. Поэтому
`alembic upgrade head` не падает ни при повторном запуске, ни на базе, где таблицы отдела
уже создал `create_all` при старте приложения.

## Локально

```bash
cd backend
alembic -c alembic.ini upgrade head      # применить
alembic -c alembic.ini current           # какая ревизия стоит
alembic -c alembic.ini downgrade base    # откатить (уберёт только таблицы отдела)
```

## На сервере

`backend/Dockerfile` включает `alembic.ini` и весь каталог `migrations` в образ API,
поэтому команды ниже работают из рабочего каталога `/app` без подключения исходников томом.

```bash
cd /opt/delo
docker compose exec api alembic -c alembic.ini upgrade head
docker compose exec api alembic -c alembic.ini current
```

Порядок на обновлении: сначала собрать и поднять новый образ, потом применить миграцию.
Том PostgreSQL не пересоздаётся, демонстрационные заявки в базе остаются.

Перед первым применением на сервере — снять копию базы:

```bash
docker compose exec db pg_dump -U delo delo > /opt/delo/backup-$(date +%F).sql
```

## Проверка

```bash
cd backend
python scripts/check_migration.py
```

Скрипт собирает базу прежней версии (таблиц отдела нет), наполняет её демонстрационными
данными и отправленной заявкой, накатывает миграцию и сверяет: новые таблицы появились,
счётчики прежних таблиц не изменились, повторный запуск не падает и ничего не дублирует,
откат убирает только наши таблицы. Второй сценарий — база, поднятая приложением, где
таблицы отдела уже существуют: миграция и там проходит без ошибок.

Записанный прогон: [MIGRATION_CHECK.txt](MIGRATION_CHECK.txt).

**Ограничение прогона.** Проверка выполнена на SQLite — локальной копии той же схемы.
PostgreSQL на машине разработки нет (Docker недоступен), и к базе сервера из рабочего
окружения доступа нет. Прогон миграции на PostgreSQL сервера с предварительным `pg_dump`
входит в тикет 04 («Версия выкачена на VPS, миграция применена к существующей базе без
потери данных»). Риск низкий: ревизия использует только переносимые типы и ничего не
меняет в существующих таблицах, — но до прогона на сервере пункт считается незакрытым.

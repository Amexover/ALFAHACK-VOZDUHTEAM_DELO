# Контракт API отдела сотрудников

Для фронтендера команды и второго разработчика бэкенда.

Документ описывает **все** ручки отдела: и те, что уже работают (тикет 01), и те, что
появятся в тикетах 02–04. Формы ответов для будущих ручек зафиксированы заранее — по ним
можно рисовать экраны, не дожидаясь логики. Если форма где-то изменится, правка приедет
в этот файл отдельным коммитом, и это будет написано в начале раздела.

Дата: 22 октября 2026. Ветка: `feat/staff-pipeline`. Версия набора правил скоринга: `RS-2026.10.1`.
Состояние: ручки тикетов 01 и 02 работают, формы сняты с живого приложения; формы тикетов
03–04 пока предварительные.

## Что важно знать до начала

**Клиентская сторона не меняется ни в чём.** Статусы заявки, роли, типы событий общей
истории и ответы клиентских ручек остаются прежними. Всё, что описано ниже, живёт только
в ручках сотрудника.

**Два слоя состояний.** У заявки есть внешний статус (`IN_REVIEW`, `NEED_INFO`, …) — его видит
клиент, и он не меняется. И есть внутренний этап конвейера (`VERIFICATION`, `UNDERWRITING`,
`DONE`) — его видит только сотрудник. Экран сотрудника строится по этапу, экран клиента — по
статусу. Не путать: внутренний этап клиенту не отдаётся никогда.

**Роли.** Общая роль пользователя (`user.role`) по-прежнему `CLIENT` или `EMPLOYEE`.
Роль внутри отдела (`department.staff_role`) — `VERIFIER` или `UNDERWRITER`, приходит отдельно
из `GET /api/staff/me`. У сотрудника может не быть роли отдела — тогда `staff_role: null`
и права сводятся к просмотру очереди.

**Вход.** Через существующую ручку `POST /api/auth/login`, ничего нового. Сессия — cookie
или `Authorization: Bearer <token>`, как раньше.

**Ошибки** — в прежнем формате: `{"error": {"code", "message", "fields"}}`.
`message` можно показывать пользователю как есть.

## Готово в тикете 01

### `GET /api/staff/me` — кто я внутри отдела

Доступ: только `EMPLOYEE`. Клиент получает 403, гость — 401.

Примеры: [staff_me_verifier.json](../api-examples/department/staff_me_verifier.json),
[staff_me_underwriter.json](../api-examples/department/staff_me_underwriter.json),
[staff_me_forbidden_403.json](../api-examples/department/staff_me_forbidden_403.json),
[staff_me_unauthorized_401.json](../api-examples/department/staff_me_unauthorized_401.json).

```json
{
  "user": { "id": 4, "login": "verifier", "full_name": "Наталья Белова",
            "first_name": "Наталья", "role": "EMPLOYEE" },
  "department": {
    "staff_role": "VERIFIER",
    "staff_role_label": "Верификатор",
    "is_verifier": true,
    "is_underwriter": false,
    "pipeline_enforced": true,
    "permissions": ["queue:view", "application:claim", "application:release",
                    "info:request", "application:pass_to_underwriting"],
    "stage_norms": [
      { "stage": "VERIFICATION", "stage_label": "Проверка сведений",
        "limit_hours": 4, "owner_staff_role": "VERIFIER" },
      { "stage": "UNDERWRITING", "stage_label": "Принятие решения",
        "limit_hours": 24, "owner_staff_role": "UNDERWRITER" }
    ],
    "stages": [
      { "stage": "VERIFICATION", "stage_label": "Проверка сведений" },
      { "stage": "UNDERWRITING", "stage_label": "Принятие решения" },
      { "stage": "DONE", "stage_label": "Обработка завершена" }
    ]
  }
}
```

`permissions` — для показа кнопок. Это подсказка интерфейсу, а не защита: сервер проверяет
те же права сам, независимо от того, что нарисовано на экране.

`pipeline_enforced` — применяются ли к учётной записи правила конвейера. У учётных записей
отдела (`verifier`, `underwriter`) — `true`. У учётной записи `staff`, существовавшей до
появления отдела, — `false`: её поведение по контракту менять нельзя, она работает в прежнем
одноэтапном режиме. Единственное новое правило, которое действует и для неё, — защита от
гонки: решение по заявке, которую взял в работу другой сотрудник, не пройдёт. Интерфейсу это
поле нужно, чтобы не рисовать такой учётной записи шаги конвейера.

Полный список значений `permissions`:

| Право | Что открывает | Кому |
|---|---|---|
| `queue:view` | очередь отдела | всем сотрудникам |
| `application:claim` | взять заявку в работу | верификатор, андеррайтер |
| `application:release` | освободить свою заявку | верификатор, андеррайтер |
| `info:request` | запросить сведения у клиента | верификатор, андеррайтер |
| `application:pass_to_underwriting` | передать заявку на решение | верификатор |
| `application:decide` | одобрить, другие условия, отказать | андеррайтер |
| `application:cancel_auto_reject` | отменить автоматический отказ | андеррайтер |

### Существующие ручки сотрудника — без изменений

`GET /api/staff/applications`, `GET /api/staff/applications/{id}`, `/reject-reasons`,
`/request-info`, `/approve`, `/counter-offer`, `/reject` работают как раньше и отдают те же
поля — ни одно поле не добавлено, не убрано и не переименовано. В тикете 02 к ним добавлены
серверные проверки этапа и исполнителя: при отказе приходят новые коды ошибок (ниже), формы
успешных ответов не изменились.

Проверяется машинно, двумя скриптами: `python scripts/check_openapi_contract.py` сверяет
описание всех 27 записанных ручек и 19 схем с выгрузкой до наших работ, а
`python scripts/check_client_contract.py` пересобирает все 29 записанных примеров ответов на
текущем коде и сверяет состав полей. Записанные прогоны —
[OPENAPI_CHECK.txt](OPENAPI_CHECK.txt) и [CLIENT_CONTRACT_CHECK.txt](CLIENT_CONTRACT_CHECK.txt).

Очередь и карточка на демо-данных отдела:
[staff_queue_with_department_demo.json](../api-examples/department/staff_queue_with_department_demo.json),
[staff_card_department_demo.json](../api-examples/department/staff_card_department_demo.json).

### Демонстрационная очередь

Сид отдела создаёт 6 заявок от 5 компаний с разным временем подачи: 5 в статусе `IN_REVIEW`,
1 в `NEED_INFO` с открытым запросом сведений, одна из них — на рефинансирование. Самая старая
подана 50 часов назад: на ней видно просрочку норматива. Сид идемпотентен и при повторном
старте ничего не дублирует.

Выключается переменной окружения `DEPARTMENT_DEMO_QUEUE=false` (например, если на сервере
нужна чистая очередь). В тестах демо-очередь не создаётся — иначе менялся бы baseline
существующих тестов.

## Тикет 02 — конвейер (этапы, взятие в работу, сроки) — готово

Все ручки раздела работают, примеры ниже сняты с живого приложения. Против предварительной
формы из тикета 01 **добавились** поля: `stage_limit_hours` и `waiting_minutes_total` в блоке
конвейера, `number` и `status` в карточке конвейера, `payload` в записях истории. Ни одно поле
не исчезло и не переименовано; предварительные образцы `planned/queue.json` и
`planned/pipeline.json` заменены настоящими примерами.

### `GET /api/staff/queue` — очередь отдела со сроками

Примеры: [queue_free.json](../api-examples/department/queue_free.json),
[queue_mine.json](../api-examples/department/queue_mine.json),
[queue_overdue.json](../api-examples/department/queue_overdue.json).

Параметры: `scope` = `free` | `mine` | `overdue` | `all` (по умолчанию `free`),
`stage` = `VERIFICATION` | `UNDERWRITING` | `DONE`, `q` — поиск по номеру заявки и названию
компании. Незнакомое значение `scope` — 422 в обычном формате ошибки.

Каждый элемент — то же краткое представление заявки, что в `GET /api/staff/applications`,
плюс `client_name`, `preliminary_rate` и блок `pipeline`:

| Поле | Смысл |
|---|---|
| `stage`, `stage_label` | внутренний этап |
| `assignee` | `{id, full_name, staff_role}` или `null`, если заявка свободна |
| `is_mine` | заявка закреплена за текущим сотрудником |
| `claimable` | можно взять в работу (свободна и этап совпадает с ролью) |
| `stage_limit_hours` | норматив текущего этапа: 4 часа на верификацию, 24 на андеррайтинг |
| `stage_entered_at`, `deadline_at` | начало этапа и срок по нормативу |
| `time_left_minutes` | остаток до срока; отрицательное значение — просрочка |
| `is_overdue` | просрочена ли |
| `waiting_for_client` | ждём ответа клиента; это время в норматив не идёт |
| `waiting_minutes_total` | сколько минут текущего этапа ушло на ожидание клиента |
| `auto_rejected` | отказ вынесен автоматически (тикет 04) |

У заявки на этапе `DONE` срока нет: `stage_limit_hours`, `deadline_at` и `time_left_minutes`
приходят `null`, `is_overdue` — `false`.

`counts` отдаёт размеры всех четырёх срезов — для бейджей на табах. Порядок элементов:
сначала просроченные, дальше по возрастанию остатка времени — самое срочное сверху.

Сроки считаются **в момент запроса**: ни планировщика, ни фоновых задач в проекте нет,
проект по-прежнему поднимается одной командой.

### `GET /api/staff/applications/{id}/pipeline` — внутренняя карточка и история

Пример: [pipeline_card.json](../api-examples/department/pipeline_card.json).

Отдельная ручка, а не поле в существующей карточке: тело чужих функций мы не меняем, чтобы
не ломать его тесты и не ловить конфликты при мерже. Экран сотрудника собирается из двух
запросов — `GET /api/staff/applications/{id}` (как сейчас) и этого.

Отдаёт `application_id`, `number`, `status`, все поля блока `pipeline` из таблицы выше (на
верхнем уровне, без обёртки), `available_actions` и `history`.

`available_actions` — что **этот** сотрудник может сделать с **этой** заявкой прямо сейчас:
`claim`, `release`, `request_info`, `pass_to_underwriting`, `approve`, `counter_offer`,
`reject`. Список собирается теми же правилами, которыми сервер проверяет сами действия, —
разойтись с поведением сервера он не может. Кнопки лучше рисовать по нему и по
`pipeline.claimable`.

`history` — внутренняя история обработки: кто взял, когда передал, кто решил. Только
добавление; правка и удаление записи обрываются на уровне сессии базы данных.
**Клиенту не отдаётся никогда и ни в каком виде.**

Типы записей: `ACCEPTED_TO_PIPELINE`, `CLAIMED`, `RELEASED`, `INFO_REQUESTED`,
`INFO_PROVIDED`, `PASSED_TO_UNDERWRITING`, `RETURNED_TO_VERIFICATION`, `DECISION_MADE`,
`AUTO_REJECTED`, `AUTO_REJECT_CANCELLED`. У каждой записи приходит готовый `label` —
подписи с сервера, по ключу в интерфейсе ничего собирать не нужно. Поля записи: `id`, `type`,
`label`, `actor_name`, `actor_staff_role`, `comment`, `payload`, `created_at`. У автоматических
записей `actor_name` — «Система».

### Действия

| Ручка | Кто | Что делает |
|---|---|---|
| `POST /api/staff/applications/{id}/claim` | верификатор на своём этапе, андеррайтер на своём | берёт свободную заявку в работу ([пример](../api-examples/department/pipeline_claimed.json)) |
| `POST /api/staff/applications/{id}/release` | тот, за кем закреплена | возвращает заявку в очередь, запись попадает в историю ([пример](../api-examples/department/pipeline_released.json)) |
| `POST /api/staff/applications/{id}/pass-to-underwriting` | верификатор | передаёт заявку на этап решения ([пример](../api-examples/department/pipeline_passed_to_underwriting.json)) |

Тело у `release` и `pass-to-underwriting` — `{"comment": "строка, необязательно"}` либо
пустое; комментарий попадает во внутреннюю историю. У `claim` тела нет. Все три отвечают тем
же телом, что `GET .../pipeline`.

После передачи на андеррайтинг исполнитель снимается — андеррайтер берёт заявку со своего
этапа сам. Так видно, кто именно принял решение, и двое не могут решать одну заявку.

### Новые коды ошибок на существующих ручках

| Код | HTTP | Когда | Пример |
|---|---|---|---|
| `ALREADY_CLAIMED` | 409 | заявку держит другой сотрудник; в `message` — кто именно | [пример](../api-examples/department/pipeline_already_claimed_409.json) |
| `NOT_ASSIGNED` | 409 | действие требует взять заявку в работу | [пример](../api-examples/department/pipeline_not_assigned_409.json) |
| `WRONG_STAGE` | 409 | действие не для текущего этапа — например, решение до верификации | [пример](../api-examples/department/pipeline_wrong_stage_409.json) |
| `STAGE_FORBIDDEN` | 403 | роль не вправе делать это здесь: верификатор решает, андеррайтер берёт чужой этап | [решение](../api-examples/department/pipeline_stage_forbidden_403.json), [взятие](../api-examples/department/pipeline_stage_forbidden_claim_403.json) |
| `INVALID_STATUS` | 409 | заявка не в том статусе, решение уже вынесено — код прежний, не новый | — |

Что это значит для интерфейса: на кнопках решения у верификатора — 403 с понятным текстом, а
не пустой экран. Кнопки рисуются по `permissions` и `available_actions`, но ошибку всё равно
надо показывать: между открытием экрана и нажатием заявку мог взять другой сотрудник.

### Что происходит само

Заявка принимается в конвейер при первом появлении у сотрудника — и в очереди, и при открытии
карточки — и получает этап `VERIFICATION`. Отсчёт норматива идёт от времени подачи, а не от
момента, когда заявку открыли. Отдельной ручки «принять в конвейер» нет, клиентская ручка
отправки не меняется.

Запрос сведений останавливает отсчёт норматива. Ответ клиента возвращает заявку на тот этап,
с которого сведения запрашивали, а не в начало: запросили на андеррайтинге — вернётся на
андеррайтинг. Время ожидания в норматив не идёт, и заявка, которая ждала клиента дольше
норматива, просроченной не становится.

Если клиент дополнил заявку после решения (действие «дополнить» на других условиях), решение
снимается и заявка возвращается на этап `VERIFICATION` с записью `RETURNED_TO_VERIFICATION`:
сведения изменились, их надо проверить заново.

## Тикет 03 — скоринг с объяснением

### `GET /api/staff/applications/{id}/scoring`

Пример: [planned/scoring.json](../api-examples/department/planned/scoring.json).

Блок `scoring` в существующей карточке остаётся с прежними полями и прежним смыслом —
существующий интерфейс не ломается. Разбор по правилам приходит этой ручкой:

- `rules[]` — по каждому правилу: `title` (формулировка для человека), `fired`
  (сработало или нет), `contribution` (вклад в балл), `details` (чем обосновано);
- `ruleset_version` — версия набора правил, по которой посчитана оценка;
- `is_snapshot` и `snapshot_reason` — отдаётся зафиксированный снимок или живой расчёт;
- `snapshots[]` — история снимков: при приёме заявки и при вынесении решения.

Правило может подсказать готовую причину отказа — `suggested_reject_reason_code`,
код из существующего справочника `/api/staff/reject-reasons`. Можно подставлять в форму отказа.

Оценка по заявке с принятым решением зафиксирована: смена версии набора правил задним числом
её не меняет.

### `POST /api/staff/applications/{id}/scoring/preview`

Пример: [planned/scoring_preview.json](../api-examples/department/planned/scoring_preview.json).

Тело: `{"amount": 900000, "term_months": 24}` — оба поля необязательны, можно менять одно.
Отвечает: как изменится оценка при других условиях. Сохранённую заявку не меняет
(это поддержка решения «предложить другие условия» вместо отказа).

## Тикет 04 — автоматический отказ и его отмена

Автоотказ — это **политика банка на этапе приёма заявки**, а не рекомендация, принявшая
решение за человека. Рекомендация в карточке остаётся советом. Окно срабатывания узкое:
рейтинг ниже 300 **и** долговая нагрузка выше 100 % выручки. Ни одна демонстрационная
компания под него не попадает.

Клиент видит обычный отказ с причиной из существующего справочника: ни баллов, ни кодов
правил, ни слова «автоматически» в клиентском ответе нет. Внутри — запись `AUTO_REJECTED`
в истории конвейера со снимком оценки и версией набора правил.

### `POST /api/staff/applications/{id}/cancel-auto-reject`

Пример: [planned/cancel_auto_reject.json](../api-examples/department/planned/cancel_auto_reject.json).

Тело: `{"reason": "обязательная строка"}`. Доступно только андеррайтеру; верификатор
получает 403. Без причины — 422 с полем `reason`. Заявка возвращается в работу, а не
создаётся заново; прежний отказ остаётся в истории неактивным решением.

## Чего в этой версии не будет

Лимитов полномочий по суммам, эскалации руководителю, дашборда аналитики и редактируемых
через интерфейс правил. Это осознанная граница версии: наполовину сделанная функция хуже
отсутствующей. Экранов под них не нужно.

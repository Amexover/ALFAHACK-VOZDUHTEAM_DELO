# Три правки безопасности перед сдачей

Правки закрывают пункты 1–3 из раздела «Что осталось до уверенной сдачи MVP»
([FRONTEND_REPORT.md](FRONTEND_REPORT.md)). Общая мысль одна: интерфейс ограничивает
корректный путь, а сервер до этих правок часть ограничений не проверял — и прямым
запросом к API их можно было обойти.

## 1. Публичный сброс данных закрыт

**Было.** `POST /api/demo/reset` (сброс базы) и `POST /api/demo/bureau` (переключение
симулятора бюро) не требуют авторизации и были доступны при включённом
`DEMO_TOOLS_ENABLED`. В коде флаг по умолчанию стоял `true`, поэтому на сервере со
старой `.env` операции открыты: человек мог вызвать их напрямую, даже если в интерфейсе
кнопки нет.

**Стало.**

- `demo_tools_enabled` по умолчанию `false` ([app/core/settings.py](../backend/app/core/settings.py)).
  При выключенном флаге обе ручки отвечают `404 NOT_FOUND`.
- Сброс остался доступен тому, у кого есть доступ к серверу — административной командой
  [scripts/demo_reset.py](../backend/scripts/demo_reset.py). Без `--yes` она ничего не делает.
- Порядок действий на сервере и проверка — в [deploy/SERVER_README.md](../deploy/SERVER_README.md).
  Контейнер API нужно пересоздать: переменные окружения он получает только при создании,
  `restart` оставит старую настройку. Том `pgdata` не затрагивается, заявки остаются.

**Как проверяется.** `tests/test_access.py::test_demo_tools_closed_by_default`: отправленная
заявка на месте, оба demo-запроса без авторизации получают `404`, симулятор бюро не
переключился, заявка по-прежнему видна сотруднику.

## 2. Проверки данных перенесены на сервер

**Было.** Три дырки, каждая проходила прямым запросом:

- ответ на запрос банка (`info-response`) проверял только спрошенные поля, а дополнение
  заявки (`supplement`) — вообще ничего: любым из них можно было стереть поле анкеты;
- по такой неполной анкете сервер позволял вынести одобрение;
- причина одобрения на API была необязательной, хотя интерфейс её требует.

**Стало.**

- Общая серверная проверка анкеты `svc.require_complete`
  ([app/services/applications.py](../backend/app/services/applications.py)) — та же, что у
  отправки заявки. При ошибке она откатывает транзакцию: клиент получает `422` с ошибками
  по полям, а в базе остаётся предыдущая корректная версия.
- Вызывается после внесения дополнений (`info-response`, `supplement` —
  ошибки под ключами `fields.<ключ>`) и перед положительным решением сотрудника
  (`approve`, `counter-offer` — ключи `business_profile.<ключ>`). Отказ по неполной анкете
  остаётся возможен: именно для этого есть причина `INSUFFICIENT_DATA`.
- Причина одобрения обязательна: `ApproveIn.comment` стал обязательным и непустым
  ([app/schemas.py](../backend/app/schemas.py)); пробелы не считаются причиной.
- Проверки стоят в зависимостях ручек
  ([app/staff_pipeline/deps.py](../backend/app/staff_pipeline/deps.py)), а не в телах функций
  `app/api/staff.py`: по контракту в этом файле правятся только сигнатуры, и
  `scripts/check_staff_file_untouched.py` это сторожит.

**Изменение контракта.** Обязательный `comment` у `/approve` — единственное намеренное
изменение описания существующей ручки. `docs/openapi.json` перегенерирован, в нём
изменилась только схема `ApproveIn`; остальные 36 путей и 24 схемы совпадают.
Состав полей ответов не изменился: `scripts/check_client_contract.py` — 29 из 29 примеров.

**Как проверяется.** `tests/test_security_fixes.py` — запросы идут прямо к API, мимо
интерфейса:

- ответ на запрос банка с пустой отраслью → `422 fields.industry`, анкета и статус
  `NEED_INFO` не изменились, запрос сведений остался открытым;
- дополнение с пустой целью → `422 fields.purpose_details`, предложение банка не аннулировано;
- одобрение и другие условия по неполной анкете → `422 business_profile.monthly_revenue`,
  решения нет, статус `IN_REVIEW`; отказ по той же заявке проходит;
- одобрение без причины и с пробелами → `422`, в истории нет события `APPROVED`.

## 3. Создание заявок защищено от одновременных запросов

**Было.** Правило «одна активная заявка на компанию и способ займа» держалось только
проверкой в коде: два одновременных запроса (две вкладки, двойной клик) могли создать
два черновика.

**Стало.**

- Правило закреплено в базе частичным уникальным индексом
  `uq_applications_active_company_mode` по `(company_id, borrowing_mode)` для активных
  статусов ([app/models.py](../backend/app/models.py)). Завершённые и отклонённые заявки
  под правило не попадают.
- Миграция [20261022_02](../backend/migrations/versions/20261022_02_active_application_unique.py)
  добавляет только индекс. Если в базе уже есть дубли, она останавливается и печатает их,
  вместо того чтобы молча править данные: какую заявку закрыть — решение бизнеса.
- Повторный запрос обрабатывается корректно: при нарушении индекса ручка создания
  возвращает уже существующий черновик с `200`
  ([app/api/applications.py](../backend/app/api/applications.py)), а не ошибку.

**Как проверяется.**

- `tests/test_security_fixes.py`: база отказывает второй активной заявке
  (`IntegrityError`), а на воспроизведённой гонке ручка возвращает тот же черновик и в
  базе остаётся одна заявка; повторное принятие предложения даёт `409 ALREADY_ACCEPTED`
  и одну запись `ACCEPTED` в истории.
- `scripts/check_migration.py` — миграция на заполненной базе, повторный запуск и откат.
- Настоящая конкурентность требует PostgreSQL:
  `python -m scripts.check_client_concurrency --isolated --base http://frontend` racing
  создание заявки, отправку и принятие предложения, и уже имевшийся
  `scripts/check_staff_concurrency.py` — одновременные решения сотрудников.

## Что ещё нужно сделать руками

1. Применить пункт 1 на сервере 195.133.41.30 по [SERVER_README.md](../deploy/SERVER_README.md):
   `.env` → `DEMO_TOOLS_ENABLED=false`, пересоздать контейнер API, проверить `404`.
2. Накатить миграцию `alembic -c alembic.ini upgrade head` на базе сервера (она добавляет
   только индекс; при дублях остановится с понятным сообщением).
3. Прогнать оба конкурентных скрипта на отдельном PostgreSQL-стенде и приложить вывод к
   приёмке: здесь они не запускались — на машине разработки нет PostgreSQL и Docker.

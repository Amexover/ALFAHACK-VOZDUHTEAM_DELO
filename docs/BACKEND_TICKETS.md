# Тикеты бэкенда

Каждый тикет — законченный кусок, который можно проверить отдельно. Формат: цель, объём работ, критерии приёмки, зависимости. Ссылки «§N» ведут на разделы клиентской инструкции, «Карта» — на `docs/PROJECT_MAP.md`.

```
T01 ─┬─ T02 ─┬─ T03 ─┬─ T04 ─ T05 ─┐
     │       │       │             ├─ T07 ─ T08 ─┬─ T09 ─┬─ T10
     │       │       └─ T06 ───────┘             │       └─ T11
     │       │                                   ├─ T12
     │       └─ T13                              └─ T14 ─ T15
```

## День 1

### T01. Каркас приложения
**Цель:** пустое приложение запускается одной командой.

- Структура `backend/app/{core,auth,companies,simulators,loans,pricing,applications,staff,content}`, `backend/tests/`.
- `core/settings.py` (pydantic-settings): `DATABASE_URL`, `SECRET_KEY`, `CORS_ORIGINS`, `BUREAU_AVAILABLE`.
- `core/db.py`: engine, session, `Base`, `create_all` при старте.
- `core/errors.py`: единый формат `{"error": {"code", "message", "fields"}}`, ошибки валидации Pydantic отдаются в этом формате (`VALIDATION_ERROR`).
- `GET /api/health`.
- `Dockerfile`, `docker-compose.yml` (`db` + `api`), `.env.example`.
- pytest: фикстура тестовой БД и `TestClient`.

**Приёмка:**
- `docker compose up` → `GET /api/health` = 200, Swagger открывается на `/docs`.
- Невалидное тело запроса возвращает 422 в едином формате.
- `pytest` проходит.

**Зависит от:** —

### T02. Модели данных и сид
**Цель:** все таблицы и демонстрационные данные.

- SQLAlchemy-модели всех таблиц из Карты.
- Идемпотентный сид при старте:
  - 3 пользователя;
  - 4 компании, рейтинги и 2 кредита;
  - 6 новостей;
  - справка;
  - причины отказа.
- Enum-ы: `Role`, `LegalForm`, `BorrowingMode`, `ProductId`, `ApplicationStatus`, `DecisionKind`, `EventType`, `NewsTag`.

**Приёмка:**
- Повторный старт не дублирует сид.
- Данные компаний и кредитов совпадают с таблицей §2.

**Зависит от:** T01

### T03. Аутентификация и роли
**Цель:** вход демо-пользователей, разделение клиента и сотрудника.

- `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`.
- Подписанная httpOnly-cookie (`itsdangerous`), хэш пароля.
- Зависимости `current_user`, `require_client`, `require_employee`.

**Приёмка:**
- Неверный пароль → 401 с понятным текстом.
- Без cookie любые `/companies*` и `/applications*` → 401.
- Клиент на `/staff/*` → 403, сотрудник на клиентских эндпоинтах → 403.
- Тест на каждый случай.

**Зависит от:** T02

### T04. Компании и симулятор реестра (§1)
**Цель:** выбор и добавление бизнеса.

- `GET /companies`: только компании текущего пользователя (название, тип, ОГРН/ОГРНИП).
- `POST /companies` {legal_form, name, ogrn}:
  - проверка формата через `simulators/registry`: ООО — 13 цифр, ИП — 15 цифр;
  - ошибки возвращаются в `fields`;
  - бюро присваивает новой компании рейтинг 600.
- Общий хелпер `get_owned_company(id, user)`: чужая или несуществующая компания → 404.

**Приёмка:**
- Добавленная компания сразу видна в списке.
- `maria` не видит компаний `alexey` ни в списке, ни по id.
- Пустое имя или неверная длина ОГРН → 422 с ошибкой у поля.
- Тест изоляции.

**Зависит от:** T03

### T05. Бюро, кредиты, дашборд (§2)
**Цель:** главная страница компании.

- `simulators/bureau`: `get_rating(company) -> Rating | None`. При `BUREAU_AVAILABLE=false` возвращает `None`.
- `GET /companies/{id}/loans`: название продукта по каталогу, выдано, остаток, ставка, дата и сумма следующего платежа.
- `GET /companies/{id}/dashboard`:
  - компания и ФИО владельца;
  - `rating` {score, band, updated_at, source_label} или `null`;
  - `loans`;
  - `active_applications` (пока пустой массив, заполнится в T08);
  - `news` (пока пустой массив, заполнится в T13).

**Приёмка:**
- Для трёх компаний Алексея рейтинг и кредиты как в §2.
- У «Маяк Трейд» `loans=[]`.
- При выключенном бюро `rating=null`, остальной ответ без ошибок.

**Зависит от:** T04

### T06. Конфиг и расчёт условий (§4, §7)
**Цель:** единый источник лимитов и формул.

- `pricing/config.py`: лимиты по `legal_form`, сроки, шаги, каталог продуктов, шкала рейтинга.
- `GET /config` отдаёт эти значения фронту.
- `pricing/service.py`:
  - `validate_amount(legal_form, amount)`: минимум, максимум, кратность 50 000;
  - `validate_term`;
  - `rate(rating, term, mode)`: правила §4, −1 п.п. для рефинансирования, 24 % без рейтинга;
  - `annuity(amount, rate, term)`: округление до рубля.
- `POST /pricing/quote` {company_id, borrowing_mode, amount?, term_months, existing_loan_id?}:
  - ответ: `rate`, `monthly_payment`, `rating_based`;
  - для `REFINANCE` сумма = остаток, плюс блок `comparison` {current_rate, current_next_payment, new_rate, new_payment, is_better}.

**Приёмка:**
- Юнит-тесты на все границы рейтинга (499/500/749/750), срока (24/25), рефинансирование, отсутствие рейтинга, расчёт аннуитета.
- Сумма выше лимита или не кратная шагу → 422.
- Кредит чужой компании в `quote` → 404.

**Зависит от:** T03

### T07. Черновик заявки (§4–§8, §15)
**Цель:** пошаговое сохранение заявки на сервере.

- `POST /companies/{id}/applications` {borrowing_mode}:
  - возвращает существующую активную заявку этого способа займа или создаёт `DRAFT`;
  - если активная заявка уже отправлена, возвращает её, и фронт ведёт клиента на статус.
- `PATCH /applications/{id}`, частичное обновление только в `DRAFT`:
  - `amount`, `term_months`;
  - `product_id`: только `NEW_CREDIT`;
  - `existing_loan_id`: только `REFINANCE`, только кредит этой компании и не занятый другой активной заявкой; сумма автоматически = остаток;
  - `business_profile` {industry, months_operating, monthly_revenue, monthly_debt_payments, purpose_details}: поля ≥ 0, целые;
  - `current_step`.
- При каждом PATCH пересчитываются `preliminary_rate` и `preliminary_payment`.
- `GET /applications/{id}`: полная сводка (компания, способ займа, продукт или выбранный кредит, параметры, анкета, статус, `current_step`).
- PATCH вне `DRAFT` → 409.

**Приёмка:**
- После повторного GET значения совпадают с сохранёнными.
- Смена `product_id` не сбрасывает сумму и срок.
- `product_id` в `REFINANCE` → 422.
- Чужая заявка → 404.
- Вторая активная заявка того же способа не создаётся.

**Зависит от:** T05, T06

### T08. Отправка, статус и история (§10, §11)
**Цель:** заявка уходит на рассмотрение, клиент видит прогресс.

- `POST /applications/{id}/submit`:
  - проверка полноты: продукт или кредит, сумма, срок, все обязательные поля анкеты; список недостающих полей возвращается в `fields`;
  - повторная проверка лимитов;
  - номер `D-2026-NNNNNN`, `submitted_at`, статус `IN_REVIEW`, событие `SUBMITTED`.
- Защита от двойного клика: блокировка строки (`SELECT … FOR UPDATE`) и проверка статуса. Повтор → 409, второй заявки не возникает.
- `GET /applications/{id}` дополняется полями `number`, `status_label`, `stage` (шкала из 4 шагов, активный вычисляет сервер), `next_steps_text` («Что дальше»), `events` (дата, действие, участник). Внутренние поля в ответ не попадают.
- `GET /companies/{id}/applications`: «Мои заявки».
- `dashboard.active_applications` заполняется.

**Приёмка:**
- Двойной submit подряд даёт один номер и одно событие (тест).
- Неполная заявка → 422 с перечнем полей.
- Статус и этап корректны.

**Зависит от:** T07

## День 2

### T09. Панель сотрудника и решения (§13)
**Цель:** банк двигает заявку.

- `GET /staff/applications?status=`: очередь (номер, компания, способ займа, сумма, статус, дата), фильтры «Все» и «На рассмотрении».
- `GET /staff/applications/{id}`: всё, что видит клиент, плюс `checks` (регистрация, бюро, полнота анкеты, долговая нагрузка), `internal_score` и `recommendation` из Карты.
- `POST …/approve` {comment}: только из `IN_REVIEW`, параметры берутся из заявки, решение `APPROVED`.
- `POST …/counter-offer` {amount, term_months, rate, comment}:
  - лимиты по форме бизнеса;
  - для `REFINANCE` сумма от 100 000 ₽ до остатка долга;
  - параметры обязаны отличаться от запрошенных, иначе 422 «используйте Одобрить».
- `POST …/reject` {reason_code, comment?}: причина из `GET /staff/reject-reasons`.
- Каждое решение пересчитывает платёж, создаёт `decision` и событие.
- Конфликт двух решений → 409.

**Приёмка:**
- Клиент в `GET /applications/{id}` видит активное решение без внутренних полей.
- Ставка в решении берётся у сотрудника, а не из предварительного расчёта.
- Для отказа клиент получает понятный текст, код ему не показывается.
- Тесты переходов и 409.

**Зависит от:** T08

### T10. «Нужны сведения» (§12)
**Цель:** диалог «запрос — ответ» на странице заявки.

- `POST /staff/applications/{id}/request-info` {message, requested_fields[]}:
  - поля только из списка полей анкеты;
  - статус `NEED_INFO`, событие.
- Клиентский `GET /applications/{id}` возвращает `info_request` {message, requested_fields} только пока статус `NEED_INFO`.
- `POST /applications/{id}/info-response` {answer_text, fields{}}:
  - `answer_text` обязателен;
  - каждое запрошенное поле обязательно и валидно;
  - обновляет снимок анкеты, статус → `IN_REVIEW`, событие с ответом.
- Повторный ответ → 409.

**Приёмка:**
- Без обязательного поля ответа → 422.
- Сотрудник в карточке видит именно отправленные клиентом данные.
- Вопрос и ответ остаются в истории.

**Зависит от:** T09

### T11. Принятие и дополнение (§13, §14)
**Цель:** завершение демонстрационного пути.

- `POST /applications/{id}/accept`:
  - только из `APPROVED` или `COUNTER_OFFER`;
  - `COMPLETED`, `completed_at`, событие;
  - в ответе итоговые параметры, номер, дата.
- Повторное принятие → 409, отказ «принять» нельзя → 409.
- `POST /applications/{id}/supplement` {answer_text, fields{}}:
  - только из `COUNTER_OFFER`;
  - решение деактивируется, анкета обновляется, статус → `IN_REVIEW`, событие.
- `COMPLETED` не создаёт записей в `existing_loans`.

**Приёмка:**
- Тесты на повторное принятие, принятие отказа, дополнение.
- После `COMPLETED` у компании можно создать новую заявку того же способа займа.

**Зависит от:** T09

### T12. Сквозная ветка рефинансирования (§6, §7)
**Цель:** рефинансирование работает так же полно, как новый кредит.

- Проверка всей цепочки: выбор кредита → сравнение условий → анкета → отправка → решение → принятие.
- Сводка и карточка сотрудника показывают выбранный кредит (название, остаток, текущая ставка).
- Для компании без кредитов `POST …/applications {REFINANCE}` → 409 с кодом `NO_LOANS_TO_REFINANCE`, чтобы фронт показал пустое состояние §6.
- Пометка о непогашенной разнице во встречном предложении (Карта, правило 5).

**Приёмка:**
- Кредит другой компании нельзя выбрать прямым запросом (тест).
- Смена кредита пересчитывает сравнение.
- `is_better=false` отдаётся честно.

**Зависит от:** T08, T09
